# Verify Tests

Check whether tests prove the behavior they claim to protect.

Apply the target repo's `Agent Operating Principles` before verification work.

## Process

1. Identify the public behavior, bug, PRD requirement, or edge case each test claims to protect.
2. Confirm the test exercises the behavior through the narrowest public interface available.
3. Check that the assertions would fail if the behavior were wrong.
4. Reject tests that are only mock-call checks, snapshots, implementation details, or smoke coverage unless that is the real contract.
5. Prefer cheap falsification first: make a temporary local mutant, run the focused test, confirm it fails for the expected reason, then restore the code immediately.
6. Run targeted mutation testing only when a mutation gate is met.
7. Report what was verified, what remains weak, and which expensive checks were skipped or run.

## Mutation Gate

Do not run mutation testing by default.

Mutation testing is allowed when one of these is true:

- the user explicitly asks for mutation testing, Stryker, or equivalent proof,
- the behavior is critical: auth, billing, permissions, data loss, security, migrations, production regressions, or other high-impact product rules,
- review shows the test could pass while the behavior is wrong,
- cheap falsification is inconclusive and the risk justifies the runtime cost.

Full-suite mutation testing requires an explicit user request. Otherwise, mutate only the smallest relevant files or tests.

## Mutation Runner

Discover existing repo support before choosing a tool:

- read `docs/agents/verification.md`, package manifests, test config, and existing mutation scripts,
- for JS/TS repos, prefer existing Stryker setup,
- for other stacks, use the repo-native mutation runner if one exists,
- do not add Stryker or any mutation dependency without user approval,
- do not invent a mutation command when the repo has not chosen one.

Before running mutation testing, state:

- the gate that allows it,
- the target behavior,
- the focused files or test command,
- the expected runtime risk.

## Safety

- Never commit intentional mutants or temporary broken code.
- Restore every manual mutant before continuing.
- Check the diff after falsification and before reporting done.
- If mutation testing produces noisy equivalent mutants, separate real test gaps from tool noise.
- If the mutation tool is unavailable, report the skipped command and use cheap falsification instead.

<not run and why | command, scope, and result>
